Why /api/recommend takes over 3 s

A deployment with about 50k users and 200k videos sees GET /api/recommend/{user} take longer than 3 seconds. This page turns the code reading in performance-analysis.md into diagrams you can click through. Nothing here was measured. The counts follow the code paths, and the queue in §3 is a simplified model.

source: docs/performance-analysis.md · code read at master@44791ec
  1. A warm user costs two store reads. A user without a usable cached list falls back to item-to-item. It handles one positive item at a time, up to context_size = 100, and each item costs two gRPC hops into the master.
  2. Every vector query waits for one slot. With the default xvec:// store, a limiter sized by master.n_jobs = 1 gates every query. Every server, every worker and the master itself share that slot.
  3. The worker that fills the cache can't keep up. It runs with --jobs 1, scans the whole user table every minute, and skips users who have no CF embedding. Those users stay on the slow path.

§3One slot for the whole cluster

Every QueryVectors that reaches xvec has to take a runtime slot first. There are master.n_jobs slots, 1 by default. Your request, other users' fallbacks and the worker's pass all wait in line for them. This is a simplified model: each query holds a slot for one tick, and the queue is first in, first out. §5Bottlenecks and fixes

Ranked by how likely each one is to explain the 3 s. Highlight dims every diagram except the parts involved. Try it applies a config fix in the panel, and every diagram updates.

B1

Online fallback: up to 200 sequential gRPC round trips through a single-slot vector store

most likely cause

A request that falls back runs item-to-item once per positive feedback item, one after another, up to context_size = 100 items. Each iteration makes two gRPC hops to the master. There, every QueryVectors waits for the xvec limiter. The limiter is sized to master.n_jobs = 1 and shared by every server, every worker and the master's own tasks, so while a worker is mid-pass, online requests wait behind it. Each response also carries 101 full neighbor vectors that the server throws away, roughly 100 × 200–400 KB per request.

Who hits it
Users with no cache.Recommend entry, plus any request whose cached list drops below n + offset after removing seen items or filtering by category. POST /api/session/recommend does the same.

B2

Many users never get an offline recommendation, so they always fall back

feeds B1

The worker skips cold-start users and users without a CF embedding. A user who first interacts after the last CF fit has no embedding until the next fit (60 min) and the next worker pass. Users inactive longer than active_user_ttl have their cache deleted. Throughput is low by default. The worker runs --jobs 1 and makes 4–5 cache round trips per user per tick just to decide whether to skip. It scans the full user table every minute. For each user it also runs uncapped item-to-item and up to 100 GetUserFeedback calls for user-to-user. At 50k users, one pass can take hours.

Who hits it
New users, users active since the last fit, returning inactive users, and anyone the worker hasn't reached yet.

B3

Every request loads the user's full feedback history

every request

GetUserFeedback(userId, now) runs with no type filter, no time window and no limit, and it selects comment and labels for every row. On a video service where every play is a read feedback, heavy users return thousands of rows. GORM deserializes each one, and SortFeedbacks then sorts them. positive_feedback_ttl is not applied on this path. Every request pays this cost, warm cache or not.

B4

gorse-in-one serves the API and trains in the same process, with n_jobs = 1

standalone only

Each cycle, the master reloads the whole dataset into RAM, rebuilds all item and user vectors, and retrains MF for 100 epochs if feedback changed. It then runs the per-user pass inline with one job. REST requests are served from the same process and share the single xvec slot, so GC and CPU pressure from training land directly on request latency. Highlighting this switches the map to gorse-in-one.

B6

Scale limits that will bite next

not the 3 s yet
  • The cache store holds about 10M score rows or hashes at 50k users. Redis memory and the collectGarbage full scans grow linearly with it.
  • xvec searches sparse vector types (tags, items, users, auto) by brute force. A user-to-user query of type items scans 50k vectors; an item-to-item query of type tags scans 200k.
  • The item and user vector collections are fully rewritten and re-optimized every cycle.
  • MariaDB as the cache store has no categories index, and GetLatestItems with categories can't use an index because of JSON_CONTAINS / @>.

§6Confirm it before changing code

Four checks that turn the top hypothesis into evidence.

  1. Turn on tracing: [tracing] enable_tracing = true, exporter = "otlp", sent to a local Jaeger or Tempo. REST (otelrestful), GORM (otelsql), Redis (redisotel) and Mongo (otelmongo) are already instrumented.

    A single slow trace then shows how the time splits between GetUserFeedback, SearchScores and the fallback RPCs.

  2. Compare a user who has a cache.Recommend entry with one who doesn't, for example a user created after the last CF fit.

    If only the second is slow, B1 and B2 are confirmed.

  3. Put the rest_api_request_seconds histogram (server/metrics.go:23) next to the worker's "complete recommendation" log lines and their update_user_count.

    That shows how far behind the offline pass is.

  4. Count the GetUserFeedback rows for the slowest users.

    If they run into the thousands, B3 matters.
